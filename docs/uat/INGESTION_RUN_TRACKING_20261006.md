# ติดตามรอบนำเข้างานที่ใช้เวลานาน — 6 ตุลาคม 2026

## ปัญหาและวิธีแก้

รอบเดิม JobThai บันทึก 10 งานสำเร็จ แต่คำขอจากหน้าเว็บหมดการเชื่อมต่อก่อนจบ ผู้ดูแลเห็นว่าไม่สำเร็จและอาจกดซ้ำ การตรวจประวัติภายหลังจึงพบ SUCCESS

ฉบับแก้คืนรหัสรอบจาก `POST /ingestion/job-runs` ทันที แล้วติดตามผลผ่าน `GET /ingestion/job-runs/:id` แยกจากคำขอยาวเดิม หน้าผู้ดูแลตรวจทุก 5 วินาที โหลดหน้าใหม่แล้วติดตามรอบเดิมต่อได้ เก็บเฉพาะรหัสรอบและคำขอในเบราว์เซอร์ ไม่เก็บค่าลับ

- ตาราง `ingestion_runs` เก็บสถานะใน Postgres เพื่อให้ API หลายเครื่องอ่านรอบเดียวกันได้ รหัสแหล่งที่กำลังทำงานมี unique index ป้องกันการเริ่มพร้อมกัน
- รหัสคำขอใช้ซ้ำได้อย่างปลอดภัย หลังคำขอขาดการเชื่อมต่อหรือรอบจบแล้วจะคืนผลเดิม กรณีคำขออีกอันเข้ามาขณะมีรอบเดิม เก็บความสัมพันธ์กับรอบเดิมด้วยเพื่อไม่สร้างรอบใหม่เมื่อลองส่งซ้ำภายหลัง
- API เดิมและงานเที่ยงคืนใช้การล็อกแหล่งเดียวกัน
- ระหว่างทำงานส่ง heartbeat ทุก 15 วินาที หากขาดเกิน 2 นาทีจะระบุว่าถูกขัดจังหวะ ไม่อ้างว่าสำเร็จ ไม่เริ่มงานเดิมอัตโนมัติ ผู้ดูแลต้องตรวจประวัติและงานที่อาจบันทึกไปแล้วก่อนเริ่มใหม่
- ผู้ใช้ทั่วไปและบริษัทเรียกช่องทางติดตามนี้ไม่ได้ ยังใช้สิทธิ์ ADMIN เดิม
- ไม่แก้สูตรทักษะ ไม่เปลี่ยนคีย์ผู้ให้บริการ และไม่ข้ามการปฏิเสธจากเว็บไซต์ต้นทาง

## ฐานข้อมูลและสำรอง

สำรองก่อนเปลี่ยนโครงสร้างยืนยัน 28 ตาราง ขนาด 233,367 ไบต์ ตรวจ archive และ checksum แล้ว ไม่ได้ทดสอบกู้คืน เพิ่มเพียงตารางติดตามและดัชนี ไม่มีการลบหรือกู้ทับข้อมูลเดิม ยืนยันหลังเพิ่มเป็น 29 ตาราง

เปิด RLS และเพิกถอนสิทธิ์ PUBLIC, anon, authenticated ของตารางใหม่ใน transaction เดียวกัน ตรวจ `publicGrants=0` และ `rls=true` แล้ว ใช้ข้อกำหนดการป้องกันตารางใน [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)

ปรับงานสำรองรายวันให้ตรวจโครงสร้างปัจจุบัน 29 ตาราง โดยคงเวลาเดิมและแจ้งเตือนเฉพาะเมื่อมีปัญหา
