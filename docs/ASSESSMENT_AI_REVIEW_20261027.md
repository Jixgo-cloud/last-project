# ผลทบทวนข้อสอบ JavaScript และการทดลองจำลองโดย AI — 27 ตุลาคม 2569

## ข้อสรุปการทบทวน

**ยังไม่ผ่านการรับรองคุณภาพสำหรับตีความเป็นความชำนาญ JavaScript โดยรวม** พบช่องว่างของ test cases, สัญญาชนิดข้อมูลคืนค่า และเฉลยที่ไม่สอดคล้องกับขอบเขต ASCII ในโจทย์ ต้องแก้ก่อนนำไปทดลองกับผู้สมัครจริง คงสถานะ `PENDING_EXPERT_REVIEW_AND_PILOT` ไว้

การตรวจนี้เป็น AI technical/content review และการจำลองคำตอบ 7 แบบ ไม่ใช่ความเห็นจากผู้เชี่ยวชาญมนุษย์หรือ pilot กับผู้สมัครจริง จำนวนผู้ทดลองมนุษย์ในงานรอบนี้ = 0 ไม่มีการอ้างค่า reliability, validity, IOC/CVI หรือความยากเชิงสถิติจากการรันโปรแกรม

ตรวจ bank v2 ใน `prisma/assessment-bank/javascript-sandbox.json`, การรันผ่าน `Judge0Client`, สูตรคะแนนใน `assessments.service.ts` และ `coding-attempt-totals.ts` เทียบกับนโยบายใน `GITHUB_SKILL_ASSESSMENT_COMPARISON.md` และ `ASSESSMENT_POLICY_IMPLEMENTATION.md` ไม่ได้แก้ bank, ฐานข้อมูล, ผลสอบเดิม หรือ deploy production

## วิธีตรวจและทดลอง

- อ่าน prompt, rubric, เฉลย และ cases ทั้งสองข้อ แล้วสร้างคำตอบผิดแบบเจาะจงเงื่อนไขที่ต้องการวัด
- รันเฉพาะโค้ดที่สร้างเองและเฉลยใน repository ด้วย Node VM (ไม่ใช่ sandbox สำหรับรับโค้ดผู้ใช้) และส่งผ่าน client ของระบบจริงไปยัง Judge0 CE ภาษา JavaScript 63
- เพิ่ม probe อิสระที่ไม่มีใน bank เพื่อแยกคำตอบถูกจริงจากคำตอบที่เพียงผ่าน cases เดิม ไม่มีการเขียน attempt จำลองเข้าระบบ production
- เก็บ SHA-256 ของ bank, เวลา, ผล local, ผล Judge0 และ infrastructure errors แยกกันใน JSON ไม่เก็บ token หรือเฉลย/hidden inputs ในรายงานผล
- คะแนนรวมด้านล่างสมมติว่าอีกข้อทำถูกเต็ม 50 คะแนน ใช้สูตรปัดทศนิยมคะแนนรายข้อ 1 ตำแหน่ง และปัดคะแนนรวมเป็นจำนวนเต็มเหมือนระบบ ไม่ใช่คะแนนของผู้สมัครจริง

คำสั่งทำซ้ำจาก root (โหมด live ต้องมี API build ปัจจุบัน):

```powershell
node scripts/review-assessment-quality.cjs
node scripts/review-assessment-quality.cjs --live
node scripts/review-assessment-quality.cjs --live --only=pal-always-true
```

## ข้อค้นพบที่ต้องแก้

### 1. Coverage ของ Two Sum ไม่ครอบคลุมข้อกำหนดสำคัญ — สูง

cases เดิมทั้งหมดมีคำตอบ จึงไม่ตรวจว่าผู้สอบคืนค่าว่างเมื่อไม่มีคู่ และไม่มีตัวอย่างที่แยกการเก็บ index แรกกับ index ล่าสุดได้จริง Probe ที่สร้างเพิ่ม `solution('1,1,2', 3)` ต้องคืน `'1,2'`; `solution('1,2,3', 99)` ต้องคืนค่าว่าง แต่คำตอบผิดทั้งสองแบบยังผ่าน bank เดิมเต็ม

ควรเพิ่ม no-pair, repeated-earlier-index, จำนวนติดลบ, ขนาดต่ำสุด และระบุขอบเขตขนาด/ค่าตัวเลข/อินพุตว่างให้ชัด ไม่ควรเพิ่มข้อกำหนดเรื่องประสิทธิภาพย้อนหลังถ้า prompt เดิมไม่ได้กำหนด

### 2. คะแนนรวมปกปิดการขาดองค์ประกอบสำคัญ — สูง

Palindrome มีผลลัพธ์ true 4 จาก 6 กรณี คำตอบคงที่จึงได้ 33.3/50 และเมื่ออีกข้อเต็มจะได้ 83/100 Rubric ระบุหลาย criteria แต่ระบบให้คะแนนตามสัดส่วน test cases ไม่ได้รายงานหรือให้คะแนนแยก criterion

ควรออกแบบ cases ให้ครอบคลุมทั้งสองผลลัพธ์และชนิดเงื่อนไข สร้าง blueprint จับคู่ criterion → cases → น้ำหนัก พร้อมเสนอเกณฑ์ขั้นต่ำขององค์ประกอบจำเป็นให้ผู้เชี่ยวชาญพิจารณา ยังไม่ควรตั้งเกณฑ์ใหม่ตามความรู้สึกหรืออ้างว่า 70 ผ่านการ calibration แล้ว การเพิ่ม false cases เพียงอย่างเดียวไม่แก้ปัญหา content coverage ทั้งหมด

### 3. เฉลยกับข้อกำหนด ASCII ไม่ตรงกัน — สูง

โจทย์ให้เก็บเฉพาะ ASCII letters/digits แต่เฉลยเรียก `toLowerCase()` ก่อนกรอง จึงเก็บอักขระ non-ASCII บางตัวที่ถูกแปลง เช่น input `Ka` หรือ `İa` ตามข้อความโจทย์ควรเหลือ `a` และได้ true แต่เฉลยได้ false

แนวทางแก้ฉบับใหม่: กรองด้วย `/[^A-Za-z0-9]/g` ก่อน lowercase หรือแก้ prompt ให้กำหนด normalization ที่ตั้งใจและใช้ตรงกันทั้งเฉลย/cases พฤติกรรม Unicode case conversion อ้างอิง [ECMAScript: String.prototype.toLowerCase](https://tc39.es/ecma262/multipage/text-processing.html#sec-string.prototype.tolowercase)

### 4. Harness ไม่ยืนยันชนิด boolean — กลาง

การพิมพ์ boolean กับ string ผ่าน stdout ได้ข้อความเหมือนกัน จึงทำให้คำตอบคืน string ผ่านทั้งหมดแม้ prompt ขอ boolean ควรใช้ typed result envelope หรือ type guard ภายใน harness ที่ตรงกับ contract ของโจทย์ ไม่ควรแก้ comparator แบบรวมทุกภาษา/ทุกข้อโดยไม่ทดสอบ regression

### 5. ความสอดคล้องกับงานและความเป็นต้นฉบับยังมีข้อจำกัด — สูงสำหรับการตีความคะแนน

Snapshot ที่บันทึกในเอกสารนโยบายพบ JavaScript ในงาน Full Stack 33/44 งาน, Frontend 29/38 และ Backend 13/20 จึงมีเหตุผลเลือกเป็นทักษะนำร่อง ตัวเลขนี้เป็นข้อมูลเดิมในระบบ ไม่ใช่การสำรวจตลาดหรือ query production ใหม่ในรอบนี้

แต่โจทย์สองข้อวัด parsing, Map/iteration และ string normalization เป็นหลัก ยังไม่วัด async/API/error handling หรือพฤติกรรมงานจริงอื่น การพบชื่อทักษะในประกาศงานไม่เพียงพอจะรับรองความครอบคลุมของแบบวัด ต้องจัดทำตารางหน้าที่งาน → พฤติกรรม → rubric ก่อนขยายการตีความ คะแนนนี้ไม่ควรรับรอง React, Node.js หรือ TypeScript

Two Sum และ Palindrome เป็นรูปแบบโจทย์แพร่หลาย ไม่มีหลักฐานในงานนี้ยืนยันความเป็นต้นฉบับตามข้อกำหนดแรกของผู้ใช้ การเปลี่ยนชื่อไม่ใช่หลักฐานความเป็นต้นฉบับ ควรพัฒนาโจทย์ตามสถานการณ์งานต้นฉบับพร้อมบันทึกแหล่งแรงบันดาลใจและประวัติผู้ร่าง แล้วทบทวนและทดลองใหม่ ไม่ได้สรุปว่ามีการคัดลอกโดยปราศจากหลักฐาน

## ผลต่อ matching / courses / ผลสอบเก่า

ระบบรับคะแนนจริงได้ถูกต้องตาม cases แต่หากข้อสอบให้คะแนนสูงกว่าความสามารถที่ตรวจได้ matching ก็อาจไม่แสดง gap และ courses อาจไม่ถูกเสนอ การตรวจ API/UI สำเร็จจึงเป็นคนละหลักฐานกับคุณภาพการวัดทักษะ

ห้ามย้อนแก้คะแนนเก่าจากผลทบทวนครั้งนี้ ข้อสอบที่แก้ต้องมี version/criteria snapshot ใหม่ และรักษาประวัติเดิม หากเจ้าของระบบต้องการประเมินซ้ำให้สร้าง attempt ใหม่ พร้อมอธิบายเหตุผลและรุ่นข้อสอบ ไม่แทนผลเดิมเงียบ ๆ

สถานะ **ยังไม่ประเมิน** ยังคงหมายถึงไม่มีผลประเมินที่ใช้ได้: ไม่แทนด้วย 0/100, ไม่อนุมานจาก GitHub และเสนอสอบก่อน คำว่า **มีผลประเมิน** เป็นสถานะการมีหลักฐาน ไม่ใช่การรับรองว่าเครื่องมือวัดผ่านการ validation แล้ว ผลจากข้อสอบร่างควรแสดงข้อจำกัดของเครื่องมือควบคู่

## แผนทดลองกับคนจริงและเกณฑ์อนุมัติ

1. ผู้เชี่ยวชาญ JavaScript/ผู้จ้างงานทบทวน blueprint และความเกี่ยวข้องกับงาน ผู้เชี่ยวชาญด้านการวัดผลทบทวน rubric และการตีความคะแนน บันทึกชื่อ บทบาท ประสบการณ์ วันที่ และเหตุผลที่ยอมรับ/แก้ไขแต่ละ criterion
2. แก้ข้อค้นพบข้างต้นใน bank รุ่นใหม่ แล้วรัน reference และ mutation tests ให้แน่ใจว่า reference ผ่าน ส่วนคำตอบผิดถูกตรวจพบ คงฉบับร่างจนกว่าจะมีหลักฐานเพียงพอ
3. ทดลองกับกลุ่มเล็กที่มีระดับประสบการณ์ต่างกันโดยได้รับความยินยอม บันทึกเวลาทำจริง จุดที่เข้าใจโจทย์ผิด ความยาก อุปกรณ์/ภาษา และข้อผิดพลาดบริการ แยกจากคะแนนความสามารถ เริ่มกลุ่มเล็กเพื่อหาปัญหาการใช้งาน ไม่ใช้จำนวนกลุ่มเล็กอ้าง reliability ของประชากร
4. ให้ผู้ตรวจมนุษย์ประเมินตัวอย่างโค้ดอย่างอิสระตาม rubric เปรียบเทียบกับ automated score วิเคราะห์กรณีผลไม่ตรงกัน รวมทั้งการผ่านผิด/ตกผิด จำนวนตัวอย่างและวิธีวิเคราะห์เชิงสถิติต้องออกแบบตามวัตถุประสงค์ ไม่สร้างตัวเลขจาก AI responses
5. เจ้าของระบบกับผู้เชี่ยวชาญกำหนด passing standard, เวลา, น้ำหนัก และขอบเขตการใช้คะแนน พร้อมบันทึกหลักฐาน ก่อนเปลี่ยน quality status และ rollout แบบรักษาข้อมูลเดิม

ใช้หลักการเชื่อมเนื้อหาข้อสอบกับทักษะของงานและมีเหตุผลรองรับ passing score ตามตัวอย่างกระบวนการ [ETS test development](https://praxis.ets.org/states/development-and-adoption.html) และ [ETS passing-score studies](https://praxis.ets.org/states/development-and-adoption/setting-requirements.html) เป็นแนวทางการออกแบบ ไม่ได้อ้างว่าระบบนี้ได้รับการรับรองจาก ETS หรือจำเป็นต้องใช้ข้อกำหนดการสอบใบอนุญาตครูโดยตรง
